Concepts

Quality-diversity (QD) optimization looks for many good solutions that differ from each other in ways the user cares about, not for one best solution. Each solution has a fitness, how good it is, and a descriptor, a few numbers (or labels) that say what kind of solution it is. An archive divides descriptor space into regions and keeps the best solution found in each, its elite. A run fills the archive.

This page describes how the package is built from five roles, how a run proceeds, and how to read its results.

The five roles

RoleAbstract typeIts jobExamples
ProblemAbstractQDProblemscore and describe a solution, draw a random oneQDProblem, Rastrigin
ArchiveAbstractArchivedecide which solutions to keepGridArchive, CVTArchive
VariationAbstractVariationmake a child from one or two parentsGaussianMutation
EmitterAbstractEmitterpropose a batch of candidates each roundVariationEmitter, CMAEmitter
AlgorithmQDAlgorithman archive and a tuple of emittersMAPElites, CMAME

Each abstract type documents a short list of required and optional functions, its contract. All generic code is written against these contracts, so any component that meets its contract works with all the others. See Extending the package.

The interface functions, such as evaluate, add! and vary, are public but not exported, because common names like evaluate clash with other packages. Call and extend them with the module name:

QualityDiversity.evaluate(prob, x)
QualityDiversity.evaluate(p::MyProblem, x) = ...

Constructors, the solving functions and the metrics are exported.

QualityDiversity.QualityDiversity — Module
QualityDiversity

Quality-diversity optimization for any genotype that can be written as a Julia type.

Five roles make up an algorithm: a problem (AbstractQDProblem), an archive (AbstractArchive), variation operators (AbstractVariation), emitters (AbstractEmitter), and the algorithm that combines them (QDAlgorithm). Each role is an abstract type with a documented set of required and optional functions.

Interface functions such as evaluate and add! are public but not exported. Extend them with qualified names:

QualityDiversity.evaluate(p::MyProblem, x) = ...

The values of keyword arguments, such as the rankers and restart rules of a CMAEmitter, are public too: ranker=QualityDiversity.ObjectiveRanker(). The benchmark problems are in QualityDiversity.Benchmarks.

Problems

The quickest way to define a problem is to wrap a function that returns the fitness and the descriptor:

using QualityDiversity
using Random: Xoshiro

f(x) = (-sum(abs2, x), clamp.((x[1], x[2]), -2, 2))      # fitness, descriptor
prob = QDProblem(f; init=rng -> randn(rng, 5), bounds=((-2, 2), (-2, 2)))
QualityDiversity.evaluate(prob, [0.5, -1.0, 0.0, 0.0, 0.0])
Evaluation{Float64, StaticArraysCore.SVector{2, Float64}, Nothing}(-1.25, [0.5, -1.0], nothing)
  • Fitness is maximized. To minimize a cost, return its negation.
  • init draws one random solution from the generator it is given; the archive is filled with such solutions before the first round.
  • bounds gives the range of each descriptor dimension, which grid-like archives divide into cells. A problem whose descriptors take discrete values gives categories instead, such as (0:5, [:small, :large]), and gets a CategoricalArchive.
  • The function may also return a third value, the phenotype: the object that the genotype produces, when it differs from the genotype. Archives store it next to the solution when they are built with phenotype= its type.

A problem with randomness in its evaluation is a StochasticQDProblem; see the noisy problems tutorial. A problem that needs its own type, for example to evaluate a whole batch at once, subtypes AbstractQDProblem.

A run

An algorithm is an archive and a tuple of emitters. One round of a run is the same for every algorithm:

for emitter in emitters
    xs  = ask(rng, emitter, archive)         # a batch of candidates
    evs = evaluate_batch(rng, problem, xs)   # their fitness and descriptors
    rs  = add_batch!(archive, xs, evs)       # what the archive did with each
    tell!(emitter, xs, evs, rs)              # the emitter learns from it
end

Different algorithms are different archives and emitters, not different loops. The functions of CommonSolve.jl run it:

alg = MAPElites(prob; dims=(10, 10), batch_size=50)
result = solve(prob, alg; budget=20_000, rng=Xoshiro(1))
QDResult after 20000 evaluations
  archive: GridArchive with 91 of 100 cells occupied
  qd_score: -168.19469254103396
  coverage: 0.91
  max_fitness: -0.002722293013079136
  mean_fitness: -1.8482933246267468

solve is init followed by solve!. To look at the state between rounds, or to stop on a condition of your own, step by hand:

state = init(prob, alg; budget=20_000, rng=Xoshiro(1))
while state.n_evals < 20_000 && coverage(state.archive) < 0.9
    step!(state)
end
state.n_evals, coverage(state.archive)
(3750, 0.9)

init copies the archive and emitters of alg, so the same algorithm can be solved several times. The budget counts evaluations; a run stops at the end of the round that reaches it. callback(state) is called after initialization and after every round.

Results

solve returns a QDResult with three fields:

  • archive: the archive of the best solutions found;
  • history: the metrics after initialization and after every round;
  • n_evals: the number of evaluations spent.
result.history[end]
(n_evals = 20000, qd_score = -168.19469254103396, coverage = 0.91, max_fitness = -0.002722293013079136, mean_fitness = -1.8482933246267468)

elites iterates over the stored solutions and their evaluations:

best_x, best_ev = argmax(e -> e[2].fitness, collect(QualityDiversity.elites(result.archive)))
best_ev
Evaluation{Float64, StaticArraysCore.SVector{2, Float64}, Nothing}(-0.002722293013079136, [0.024911987688377144, -0.036986867330716516], nothing)

Metrics

MetricMeaning
coveragefraction of the cells that hold a solution
max_fitnessfitness of the best elite
mean_fitnessmean fitness of the elites
qd_scoresum of the fitness of the elites, each raised by offset
cqd_scorecontinuous QD score, which does not depend on the cells

The QD score sums fitness over the cells, so a negative fitness would lower it when a cell is filled. qd_score(archive; offset) adds offset to every elite; it should make every attainable fitness non-negative. A problem can supply its offset with fitness_offset, which the history uses.

Archives with several objectives have metrics of their own, such as the MOQD score; see ParetoGridArchive.

Randomness and threads

Every function that draws random numbers takes the generator as its first argument, and a run takes its generator as rng. A run with a seeded generator is reproducible:

a = solve(prob, alg; budget=5_000, rng=Xoshiro(7))
b = solve(prob, alg; budget=5_000, rng=Xoshiro(7))
a.history == b.history
true

The default evaluate_batch evaluates the solutions of a batch on several threads (start Julia with --threads=auto to use them), so evaluate must be thread-safe. The results do not depend on the number of threads: a stochastic problem draws one seed per solution from the run's generator before the threaded section, in the order of the batch. Evaluation is the only part that runs on several threads; the archive and the emitters run on one.
