Device archives and emitters

These types run MAP-Elites and CMA-ME with the archive in the arrays of a GPU; see the GPU guide. Their kernels need KernelAbstractions.jl, which the GPU packages load.

Archives

QualityDiversity.DeviceCellArchive — Type
DeviceCellArchive{T,F,N}

Supertype of the archives that keep their cells in the arrays of a device, for MAP-Elites on a GPU: DeviceGridArchive and DeviceCVTArchive. They have the cells and the rules of their host counterparts, GridArchive and CVTArchive, and differ from each other only in how a descriptor is assigned to a cell. They store solutions that are real vectors of a fixed length with entries of a floating-point type T, fitness values of type F, and descriptors with N components, and no phenotypes.

The device is chosen by the array type that the archive is built with: CuArray (CUDA.jl), ROCArray (AMDGPU.jl), oneArray (oneAPI.jl), or Array, which runs the same kernels on the CPU. The kernels that insert solutions and that vary them in a DeviceVariationEmitter are written with KernelAbstractions.jl, which every GPU package above loads; with Array load it yourself (using KernelAbstractions). The cell of a descriptor is computed in Float64, as on the host, so that both assign the same cells; a device without Float64, such as an Apple GPU, cannot run it.

Storage is one array per field, on the device: the genotypes as a dim × cells matrix, the descriptors as an N × cells matrix of T, the fitness values, which cells are occupied, and the occupied cells in increasing order, from which parents are drawn uniformly.

add_batch! follows the rule of the host cell archives: every result is computed against the archive as it was before the batch, and of the solutions that enter a cell the best is kept, the first in the batch on a tie. A fitness value that is NaN or infinite throws an ArgumentError, as does a descriptor outside the bounds with ThrowOutside() or a NaN component with ClampOutside(), before the archive changes.

The other functions of the archive contract work on the host: add! adds one solution through add_batch!, and elites and sample_elites copy the archive to the host first. The metrics are reductions on the device. Consumer GPUs compute Float64 many times more slowly than Float32: use genotype=Vector{Float32} and fitness=Float32 there.

A subtype has these fields, which the shared methods and kernels use: lower and upper (SVector{N,Float64}), outside (an OutsidePolicy), and the device arrays that device_storage allocates, with count, the number of occupied cells.

QualityDiversity.DeviceGridArchive — Type
DeviceGridArchive{T,F}(device, dims, bounds, dim; outside=ThrowOutside())
DeviceGridArchive(prob::AbstractQDProblem; dims, device, bounds=descriptor_bounds(prob),
                  genotype=Vector{Float64}, fitness=Float64, outside=ThrowOutside())

A GridArchive held in the arrays of a device, for MAP-Elites on a GPU: the same cells and rules, for solutions that are real vectors of length dim with entries of a floating-point type T, and fitness values of type F. device is the array type to store them in, such as CuArray; see DeviceCellArchive for the storage, the kernels and what runs on the host. The second form takes T from genotype, F from fitness and dim from random_solution(rng, prob).

MAPElites with device builds this archive with a DeviceVariationEmitter. GridArchive(archive) returns a host copy, for example to plot it.

Example

using CUDA
prob = Rastrigin(20)
alg = MAPElites(prob; dims=(100, 100), batch_size=10_000, device=CuArray,
                genotype=Vector{Float32}, fitness=Float32, variation=GaussianMutation(0.5f0))
result = solve(prob, alg; budget=1_000_000, rng=Xoshiro(1))
coverage(result.archive), GridArchive(result.archive)

QualityDiversity.DeviceCVTArchive — Type
DeviceCVTArchive{T,F}(device, centroids, bounds, dim; outside=ThrowOutside())
DeviceCVTArchive{T,F}(device, rng, cells, bounds, dim; samples=100_000,
                      max_iterations=100, outside=ThrowOutside())
DeviceCVTArchive(rng, prob::AbstractQDProblem; cells, device, bounds=descriptor_bounds(prob),
                 samples=100_000, genotype=Vector{Float64}, fitness=Float64,
                 outside=ThrowOutside())

A CVTArchive held in the arrays of a device, for MAP-Elites on a GPU: the Voronoi cells of a set of centroids, with the rules of the host archive, for solutions that are real vectors of length dim with entries of a floating-point type T, and fitness values of type F. device is the array type to store them in, such as CuArray; see DeviceCellArchive for the storage, the kernels and what runs on the host.

The centroids are given, or chosen on the host by k-means from samples uniform points of the box bounds, exactly as for a CVTArchive: the same centroids, or the same generator and seed, give the same cells, and centroids(archive) returns them. The last form takes T from genotype, F from fitness and dim from random_solution(rng, prob).

On the device, the box is divided into a regular grid of about as many buckets as cells, and each bucket lists the centroids that can be nearest to a point in it, computed once on the host. A kernel finds the bucket of a descriptor and compares it with those centroids only, one thread per solution. The distances are computed in Float64 in the order of the host archive's k-d tree, so the two assign the same cell, the lowest index if two centroids are equally near. In many descriptor dimensions the buckets hold more centroids, and in the limit one bucket holds all of them.

MAPElites(archive) runs MAP-Elites over it with a DeviceVariationEmitter. CVTArchive(archive) returns a host copy, for example to plot it.

Example

using CUDA
prob = Rastrigin(20)
archive = DeviceCVTArchive(Xoshiro(1), prob; cells=10_000, device=CuArray,
                           genotype=Vector{Float32}, fitness=Float32)
alg = MAPElites(archive; batch_size=10_000, variation=GaussianMutation(0.5f0))
result = solve(prob, alg; budget=1_000_000, rng=Xoshiro(2))

Batches

QualityDiversity.DeviceBatch — Type
DeviceBatch(X::AbstractMatrix)

A batch of real-vector solutions held as the columns of the matrix X, which may be a device array. It is an AbstractVector whose jth element is view(X, :, j); parent(batch) returns X. A DeviceVariationEmitter returns its candidates as a DeviceBatch, and evaluate_batch and add_batch! of a DeviceCellArchive take it without copying it to the host. A problem that scores a batch with array operations defines evaluate_batch(prob, xs::DeviceBatch) and works on parent(xs).

source
QualityDiversity.EvaluationBatch — Type
EvaluationBatch{N}(fitness::AbstractVector, descriptors::AbstractMatrix)

The evaluations of a batch of solutions as two arrays, which may be device arrays: the fitness of solution j is fitness[j] and its descriptor the column descriptors[:, j], with N rows. It is an AbstractVector of Evaluations with SVector{N,Float64} descriptors and no phenotype; reading one element copies it to the host. The default evaluate_batch of a DeviceBatch returns one, and add_batch! of a DeviceCellArchive reads its arrays where they are.

source
QualityDiversity.AddResultBatch — Type
AddResultBatch{F}

The results of add_batch! on a DeviceCellArchive for a DeviceBatch: an AbstractVector of AddResults whose fields are kept in two arrays on the device, status (the AddStatus as a UInt8) and improvement. Reading one element copies it to the host; collect copies all of them.

Emitters

QualityDiversity.DeviceVariationEmitter — Type
DeviceVariationEmitter(op; batch_size)

The emitter of MAP-Elites over a DeviceCellArchive: it draws parents uniformly from the occupied cells and applies the variation operator op, giving batch_size children, all on the device. The children come back as a DeviceBatch, which evaluate_batch and add_batch! take without copying it to the host. A later ask returns a new batch, so a batch stays valid after the next one is drawn.

op is a GaussianMutation or an IsoLineVariation; its standard deviations are converted to the element type of the archive. Each ask draws one UInt64 from the run's generator, and the kernels derive their random numbers from it with the counter-based generator Philox4x32-10, keyed on the child and the entry, so a run is reproducible from its seed on a given backend however the threads are scheduled. These random numbers differ from those of a VariationEmitter on the host.

source
QualityDiversity.DeviceCMAEmitter — Type
DeviceCMAEmitter(dim; num_searches, sigma0, kwargs...)

The emitter of CMA-ME over a DeviceCellArchive: num_searches independent CMA-ES searches, each a CMAEmitter with the keyword arguments of CMAEmitter, that ask together. Their candidates form one batch, which is evaluated and added to the archive on the device at once, so every search of a round sees the archive as it was before the round, as in pyribs. A host CMAME instead steps its emitters one after another, as in the CMA-ME paper. The searches that restart draw their new starts from the archive together, at the start of the round. A device only pays off with many searches, or many candidates per search: the batch has num_searches times the batch size of one search.

The searches stay on the host: each draws its candidates from its own distribution, the searches in parallel on the threads of the host, each with a generator seeded by a number drawn in order from the run's generator, so that a run is reproducible from its seed whatever the number of threads. The batch is then copied to the device. After the batch is added, its fitness values, descriptors and results are copied back once, and each search ranks its part and adapts its distribution as a CMAEmitter does, the searches in parallel on the threads of the host.

The property searches holds the searches, for example to read their iterations and restarts.
